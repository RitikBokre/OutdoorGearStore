# Decisions

The main decision I could have gone either way on was the product details section. Tabs and accordions both fit the brief. An accordion is often nicer on mobile because it keeps every section close to the user's scroll position, but this PDP has only three concise panels and the desktop layout benefits from a more stable below-fold area. I chose tabs so the section feels closer to a premium retail PDP: compact, predictable, and easy to scan without expanding multiple regions. The selected tab is persisted in localStorage because the assignment asks for persistent UI state, and this is a small but useful preference to retain across refreshes.

I also split product data into two sources. The base product record comes from Fake Store API, which satisfies the external data requirement and gives the page a real loading and error path. Variant inventory, color swatches, gallery imagery, specifications, and reviews are local enhancement data because Fake Store does not model those details. In a production system, those would come from a commerce API or CMS rather than a static module, but keeping them local here makes the app deterministic and lets the UI cover sold out, low stock, quantity caps, and deep-linked variant selection cleanly.

With more time, I would add tests around cart rehydration, URL synchronization, and variant stock caps. Those are the highest-risk behaviors because they cross browser APIs, React state, and user actions. I would also improve the gallery with responsive image sizes, keyboard arrow navigation, and a more robust mobile thumbnail position indicator tied to scroll position rather than only the active thumbnail click. Finally, I would introduce a product adapter layer so the Fake Store response and local merchandising data are normalized before components receive them. The current structure is intentionally straightforward, but an adapter would scale better if this grew into a category page or multiple PDP routes.
